## 二、问题1:USB VBUS 供电 regulator 依然是 dummy,未生效

### 验证命令
```sh
dmesg | grep -iE "usb|xhci|regulator" | tail -30
```

### 实际输出(问题证据)
```

[    2.765094] usbcore: registered new interface driver usbfs

[    2.775998] usbcore: registered new device driver usb
[    2.794255] xhci-mtk 11200000.usb: supply vbus not found, using dummy regulator

```

**关键行**:
```
xhci-mtk 11200000.usb: supply vbus not found, using dummy regulator
```

这行与刷机前(旧V2固件)的表现**完全一致**,说明本次交付固件中对USB供电的DTS修复**并未生效**。

### 与交付说明的差异

交付的《刷机教程.md》第0节声称:
> 设备树新增 USB VBUS 5V 供电(GPIO23,fixed-regulator)并把 `vbus-supply` 挂到 `&xhci`
> → 已验证 .itb 内核 DTB 中含 `regulator-usb-vbus` / `usb_vbus` / `vbus-supply` 节点

但实际运行时内核日志显示 **`supply vbus not found`**,即内核在查找名为 `vbus` 的 supply 属性(对应设备树里 xhci 节点下的 `vbus-supply` 属性)时**没有找到**,因而退回 dummy regulator。

这说明可能存在以下情况之一,需要开发者排查:
1. DTS里确实添加了 `regulator-usb-vbus` 定义节点,但**没有正确地把这个regulator通过 `vbus-supply` 属性关联到实际使用它的 `&xhci` 节点**(节点定义了,但引用关系没接上)
2. 或者DTS改动没有被正确编译进最终产物的DTB里(编译流程/patch应用问题,导致声称的改动实际未包含在这次生成的.itb文件中)
3. 或者 regulator 节点命名/属性名与内核期望的不一致(内核具体寻找的supply名称是 `vbus`,需要确认DTS里定义的完全匹配)

**建议开发者操作**:重新用 `dtc` 反编译交付的这个.itb文件里实际打包的DTB,人工核对其中是否真的存在 `vbus-supply` 属性且已挂载到xhci节点,而不仅是core dtsi源码层面有改动。

## 三、问题2:承诺预装的USB网络共享驱动缺失

### 验证命令
```sh
apk info 2>/dev/null | grep usb
```

### 实际已安装驱动
```
kmod-usb-common
kmod-usb-core
kmod-usb-storage
kmod-usb-xhci-hcd
kmod-usb-xhci-mtk
kmod-usb3
```

### 交付说明承诺应包含(《刷机教程.md》第0节)
```
kmod-usb3、kmod-usb-xhci-mtk、kmod-usb-net、kmod-usb-net-cdc-ether、
kmod-usb-net-rndis、kmod-usb-net-cdc-ncm、kmod-usb-acm、
kmod-usb-storage、kmod-usb-storage-uas、block-mount
```

### 缺失清单

| 驱动包 | 状态 |
|---|---|
| `kmod-usb-net` | ❌ 缺失 |
| `kmod-usb-net-cdc-ether` | ❌ 缺失(中兴F50等CDC-Ether模式USB共享网络的核心驱动) |
| `kmod-usb-net-rndis` | ❌ 缺失 |
| `kmod-usb-net-cdc-ncm` | ❌ 缺失 |
| `kmod-usb-acm` | ❌ 缺失 |
| `kmod-usb-storage-uas` | ❌ 缺失 |
| `block-mount` | ❌ 缺失 |

**即便本次VBUS供电问题得以解决、USB口能正常供电,由于`kmod-usb-net-cdc-ether`等驱动缺失,中兴F50依然无法被内核识别为网络设备(不会生成`usb0`/`eth2`等网卡)。**

这说明交付物中的 `manifest` 文件(包清单)与实际固件内**真正安装的软件包不一致**,需要开发者检查:
1. 编译时的 `.config` 或 `make menuconfig` 选择的软件包列表,是否真的包含了这些`kmod-usb-net-*`系列驱动
2. 或者这些驱动是否被编译成了独立的 `.ipk/.apk` 包但没有被打入这次的sysupgrade镜像(常见于"生成了但没勾选进固件镜像内置"的疏漏)

## 四、给开发者/AI编译工具的具体建议

1. **重新反编译本次实际交付的.itb文件**(而非只看源码/patch文件层面的改动),确认:
   - DTB中 `vbus-supply` 属性是否真的存在且正确关联到 `&xhci` 节点
   - 编译产物中是否真的包含上述缺失的 `kmod-usb-net-*` 系列.ko驱动文件

2. **建议编译后自行做一次刷机验证**,而不是仅凭源码/patch改动就断定修复完成——本次报告的两个问题都是"源码层面看似已改,但实际产物中未生效/未包含"的典型案例,唯有实机刷入并跑 `dmesg`/`apk info` 才能确认。

3. 如果第1点排查后发现是regulator命名或引用关系问题,可参考同ODM平台其他已知USB供电正常的设备(如小米WR30U、H3C Magic NX30 Pro)的DTB反编译结果,对照 `vbus-supply` 的具体写法。

4. 麻烦这次修复完成后,**提供反编译DTB中相关USB节点的截图或文本**,以及**编译时实际生成的完整ipk/apk包列表**,作为二次验证的依据,避免再次出现"文档描述与实际产物不符"的情况。
