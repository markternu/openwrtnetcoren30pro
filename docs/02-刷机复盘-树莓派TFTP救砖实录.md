# Netcore N30 Pro 刷机全过程复盘教程
### 用树莓派 + MacBook 联合调试,TFTP救砖刷入ImmortalWrt完整实录

---

## 零、背景与目标

- 路由器:Netcore N30 Pro(MediaTek Filogic平台),原厂固件
- 目标:刷入 ImmortalWrt(第三方SamZong233编译版,修复LAN口和USB问题)
- 工具:一台 MacBook + 一台 树莓派4B(做TFTP服务器和网络中转)
- 最终结果:刷机成功,5个LAN口识别正常;USB供电问题仍存在(已整理成单独技术报告)

---

## 一、整体架构思路

```
路由器(刷机对象) ──网线── 树莓派(TFTP服务器,eth0接路由器)
                              │
                          WiFi连接家里路由器
                              │
                            MacBook(远程SSH操作树莓派)
```

**核心逻辑**:树莓派同时用两张网卡——`eth0` 专门接"待刷路由器"做静态IP+TFTP服务器,`wlan0` 连接家里正常网络,保证MacBook能一直远程SSH操作树莓派,不会因为eth0那边的折腾断线。

这个"双网卡分工"的思路是对的,但**实际操作中,因为eth0和wlan0经常处于同一个 `192.168.1.0/24` 网段,反复引发路由冲突,是这次刷机过程中踩坑最多的地方**,下面详细复盘。

## 二、准备阶段

### 2.1 下载系统镜像要用对下载方式

最开始从树莓派官网下载系统镜像,网页下载慢,尝试转到云服务器上用 `wget` 下载,结果报错 `Permission denied`。

**原因**:在没有写权限的目录(如 `/var/www/html`)执行 `wget`,不是网络问题。

**解决**:换到有写权限的目录(如 `~`)执行下载,或用 `chown` 调整目录权限。

### 2.2 确认下载的镜像版本

树莓派官网下载页面会有 Lite / 标准(带桌面)/ Full 三种版本,注意区分:
- **Lite**:无桌面,纯命令行,体积最小(几百MB)
- **标准版(本次使用)**:带 Raspberry Pi Desktop 桌面,约1.3GB下载/6GB存储需求
- **Full**:带桌面+更多预装软件,体积最大

用 `shasum -a 256` 校验下载文件的SHA256,确保和官网一致,避免文件损坏。

### 2.3 烧录工具选择:balenaEtcher 踩坑,换 Raspberry Pi Imager 解决

**坑1**:用 balenaEtcher 烧录时报错"镜像被压缩"之类的错误,即使文件SHA256校验完全正确。

**排查过程**:
- 先确认文件完整性(SHA256一致,排除下载损坏)
- 尝试确认Etcher是否支持直接烧录`.img.xz`(支持,不需要手动解压)
- 最终解决:**换成树莓派官方的 Raspberry Pi Imager 工具**,一次烧录成功

**经验**:遇到烧录工具报错,如果文件校验没问题,优先换官方工具,比排查第三方工具兼容性问题更快。

**加分技巧**:Raspberry Pi Imager 烧录时可以点击设置图标,**提前配置好WiFi、SSH、用户名密码**,烧完开机就能直接远程连接,不需要额外接显示器键盘配置——这个技巧在后续"重新烧录"环节发挥了重要作用。

## 三、TFTP救砖:环境搭建阶段

### 3.1 基础思路

路由器刷入无WebUI的官方u-boot后,唯一的救砖方式是**u-boot自动TFTP拉取固件**。需要:
1. 树莓派开TFTP服务
2. 树莓派eth0设置静态IP `192.168.1.254`(u-boot期望在这个地址找TFTP服务器)
3. 把固件文件放到TFTP目录,**文件名必须和u-boot期望的完全一致**
4. 路由器断电、长按Reset、通电,进入u-boot的TFTP恢复模式

### 3.2 安装配置 tftpd-hpa

```bash
sudo apt install -y tftpd-hpa
sudo mkdir -p /srv/tftp
sudo chmod 755 /srv/tftp
sudo tee /etc/default/tftpd-hpa > /dev/null <<'EOF'
TFTP_USERNAME="tftp"
TFTP_DIRECTORY="/srv/tftp"
TFTP_ADDRESS="0.0.0.0:69"
TFTP_OPTIONS="--secure --create"
EOF
sudo systemctl restart tftpd-hpa
```

### 3.3 坑2:文件命名规则,不同设备/不同u-boot版本要求不同

最初参考的中文博客教程说,u-boot 请求的文件名固定是:
```
immortalwrt-mediatek-filogic-netis_nx30v2-initramfs.itb
```

但**实测通过 `tcpdump` 抓包发现,这台设备的u-boot实际请求的是**:
```
immortalwrt-mediatek-filogic-netis_nx30v2-squashfs-sysupgrade.itb
```

**注意两点关键差异**:
1. 文件名格式是 `squashfs-sysupgrade` 而不是 `initramfs`——意味着这个精简u-boot是**直接把下载的文件写入flash**,不是先跑一个内存里的临时系统过渡
2. **不同设备、不同版本的u-boot,请求的具体文件名可能不一样**,不能完全信教程,必须**用 `tcpdump` 实际抓包确认**

**排查方法(强烈建议养成习惯)**:
```bash
sudo tcpdump -i eth0 -n udp port 69
```
在路由器进入救砖模式后抓包,直接看 `RRQ "文件名"` 这一行,以实际抓到的为准,把TFTP目录里的文件复制一份改成这个确切文件名。

### 3.4 坑3:19字节UDP包 = "文件不存在"的错误提示,容易被忽略

当TFTP目录里没有对应文件名的文件时,`tcpdump` 会显示类似:
```
IP 192.168.1.1.xxx > 192.168.1.254.69: TFTP, RRQ "xxx.itb"
IP 192.168.1.254.xxx > 192.168.1.1.xxx: UDP, length 19
```
这个**19字节的UDP回包,是tftpd返回的"文件不存在"错误包**,不是正常传输。正常传输应该是持续的、大小在1000-1472字节左右的DATA包。

**排查技巧**:如果看到"一问一答但都是几十字节的小包"反复循环,基本可以确定是文件名不匹配,不是网络问题。

## 四、核心难题:eth0/wlan0 同网段路由冲突(本次刷机踩坑最多的部分)

这是整个过程中**反复出现、耗时最长**的问题,值得系统梳理。

### 4.1 问题本质

树莓派需要:
- `wlan0` 连家里WiFi,网段是 `192.168.1.0/24`,网关 `192.168.1.1`(你家真正的路由器)
- `eth0` 接待刷路由器,静态IP `192.168.1.254`,同样是 `192.168.1.0/24` 网段

**当两张网卡在同一个IP网段时,Linux内核的路由选择会产生歧义**——尤其是待刷的路由器**自己的地址也是 `192.168.1.1`**(和你家真正路由器撞了),导致内核经常无法正确判断某个目的地(尤其是 `192.168.1.1`)该走哪张网卡。

### 4.2 踩坑记录与逐次改进方案

**第一次尝试**:直接 `nmcli con add ... ip4 192.168.1.254/24 gw4 192.168.1.1`
- **翻车**:立刻抢占默认路由,SSH连接断线,而且是通过原本那条SSH连接执行命令的,直接把自己反锁在外面

**第二次尝试**:加 `ipv4.route-metric 200` 降低eth0优先级
- **翻车**:因为是用同一个网口(eth0本身)的SSH连接来执行命令改eth0自己的配置,操作过程中网络抖动直接把连接搞断,来回折腾

**关键认知转折点**:必须用**两张不同网卡分别承担"SSH远程操作通道"和"待刷设备通信通道"**,不能用同一张网卡自己改自己。**在此之后,统一改用WiFi(wlan0)的IP来维持SSH会话,eth0只用来单独配置**。

**第三次尝试**:去掉 `gw4` 参数,只给eth0挂 `/24` 网段地址,不设网关
- **翻车**:虽然没有网关,但 `192.168.1.0/24` 这个网段路由本身还是被同时加到了eth0和wlan0上,两条路由的metric如果eth0更小,内核依然会优先选eth0作为该网段的出口,导致**从Mac发给树莓派wlan0地址的SSH流量,树莓派回包时错误地从eth0送出**,造成"连接卡住无响应"(不是直接断开,是双方各自等待,更难排查)

**第四次尝试**:改用 `/32` 主机地址 + 精确路由,只描述"如何到达router这一个IP"
```bash
sudo ip addr add 192.168.1.254/32 dev eth0
sudo ip route add 192.168.1.1/32 dev eth0
```
- **效果**:这次终于不再产生大范围的 `/24` 网段路由冲突,SSH总算稳定了一段时间

**第五次问题**:先前调整过 `ipv4.route-metric 700` 让eth0整体优先级降到最低,结果这次**副作用是给"192.168.1.1"发消息时,内核统一选择了metric更低的wlan0**,导致树莓派**回复不了TFTP请求**(路由器发来的TFTP请求虽然通过eth0被树莓派收到,但树莓派回复时包从wlan0送出去了,根本到不了路由器),外在表现是: **能用 `tftp 192.168.1.254` 自己连自己成功,但路由器那边永远收不到回复,一直重试**

**最终方案(稳定生效)**:专门给 `192.168.1.1/32` 加一条**独立于`/24`网段路由之外的精确主机路由,并显式设置很小的metric(如50)使其优先级最高**:
```bash
sudo ip route add 192.168.1.1/32 dev eth0 metric 50
```
这条路由**只影响"发往192.168.1.1这一个具体地址"的流量**,不影响 `192.168.1.0/24` 这个网段其余部分的路由决策,也不和默认路由冲突,SSH(走的是`192.168.1.165`这个不同地址)完全不受影响。

**但引出了新问题**:这条 `192.168.1.1 dev eth0` 路由**同时也会劫持树莓派自己"访问外网"时经过的默认网关流量**(因为你家真正的路由器网关恰好也是192.168.1.1),导致**树莓派临时性断网**,无法下载文件、无法apt/wget。

**应对方式**:这条精确路由**按需临时添加/删除**——
- 需要和"变砖路由器"通信(TFTP传输、ping测试)时:加上这条路由
- 需要联网下载文件时:先删掉这条路由恢复上网,下载完再加回去

```bash
# 临时删除,恢复上网
sudo ip route del 192.168.1.1 dev eth0

# 用完之后重新加回,继续跟路由器通信
sudo ip route add 192.168.1.1/32 dev eth0 metric 50
```

### 4.3 这部分的核心经验总结

1. **两个不同的物理设备撞了同一个IP(都是192.168.1.1),是本次绝大多数网络诡异问题的根源**,遇到类似情况第一时间要意识到这一点
2. **`ipv4.route-metric` 和 `ipv4.never-default` 这类参数管的是"默认路由"(0.0.0.0/0),不管"同网段内的路由选择"**,这是很多人(包括这次的我们)会踩的认知误区
3. 精确的 `/32` 主机路由 + 合理的metric,是解决"两张网卡同网段/IP冲突"问题最可靠的手段
4. **任何时候修改网络配置,都要用一个不受影响的独立通道(比如另一张网卡)来维持控制权限**,不要用自己正在改的这条链路来执行修改命令

## 五、坑4:nmcli 一些反直觉的行为

- `nmcli con add` **默认会自动激活(autoconnect=yes)新建的连接**,如果新连接配置有问题,添加命令本身就可能导致网络抖动/卡死,不是只有 `con up` 才会触发激活
- `nmcli con up "连接名"` 报错 `No suitable device found`,通常是这个连接配置内部记录的设备关联和实际网卡状态对不上了(常见于反复 `managed no`/`managed yes` 切换之后),遇到这种情况**直接删除重建**比排查修复更快

## 六、坑5:eth0接口卡死在DOWN状态,排查未果,最终重新烧录系统解决

在反复折腾网络配置后,某次遇到 `eth0` 状态死锁在 `DOWN`,`ip link set eth0 up` 命令执行了但不生效,`nmcli` 激活也全部失败(`No suitable device found`)。

**排查过的方向**(均未查出根因):
- rfkill软件锁(排除,rfkill只管无线和蓝牙)
- dmesg内核日志(信息量太大,手动排查效率低)
- 怀疑物理网线/网口问题(换接正常路由器测试来验证)

**最终决策**:与其继续深挖排查,**直接用 Raspberry Pi Imager 重新烧录一份全新系统**,是这种场景下更省时间的选择。

**经验**:网络配置这类问题,当排查成本明显超过重新烧录系统的成本时,**果断重装比坚持debug更划算**——尤其是在整个折腾过程中已经执行过大量 `nmcli device set managed no/yes`、手动`ip addr`等非常规操作、状态已经很难复原的情况下。

**重烧录后的加分项**:这次用Imager提前配置好WiFi+SSH,开机后**直接能通过WiFi的IP远程SSH连接**,不再需要先解决"eth0联网、wlan0没启用"这种先有鸡还是先有蛋的问题——这是从第一次失败中吸取的直接经验。

## 七、坑6:SSH host key 变化警告

每次树莓派重新烧录系统,或者IP复用到了之前用过的地址,SSH都会报:
```
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```
这是正常现象(不是安全问题,是本机 `known_hosts` 里记录的旧host key和新系统的不一致),处理方法:
```bash
ssh-keygen -R <对应IP>
```
清除旧记录后重新连接,确认 `yes` 添加新的host key即可。

## 八、坑7:救砖临时系统里 scp 失败

进入initramfs临时救援系统后,用 `scp` 从树莓派传文件过去,报错:
```
ash: /usr/libexec/sftp-server: not found
scp: Connection closed
```

**原因**:现代版本的 `scp` 默认走SFTP协议,依赖对端有 `sftp-server` 组件,而精简的救援系统裁掉了这个组件。

**解决**:加 `-O` 参数强制scp走旧版SCP协议(不依赖sftp-server):
```bash
scp -O 本地文件路径 root@192.168.1.1:/tmp/
```

## 九、坑8:刷机后未正常关机导致overlay配置损坏,不得不重刷一遍

第一次成功刷入固件后,**没有设置root密码就直接给路由器断电**。

**后果**:下次通电后,路由器能ping通(内核/基础网络栈正常),但:
- 所有服务端口全部无响应(SSH、HTTP全部连不上,`nmap -Pn` 扫描1000个端口全部filtered)
- WiFi没有信号
- 网页/终端反复尝试连接均卡死无响应

**根因判断**:OpenWrt使用overlay文件系统保存配置,**非正常断电(直接拔电源而不是执行 `reboot`/`poweroff`)容易导致overlay写入不完整/损坏**,虽然系统内核能跑起来,但上层依赖配置读取的服务(dropbear/uhttpd等)因为配置损坏而起不来。

**尝试过的修复方向**:
- 进入failsafe模式(未成功,时机不好把握)
- 直接重新走一遍TFTP刷机流程(最终选择的方案,更可靠)

**核心经验:刷机/改配置后,必须用 `reboot` 命令正常重启一次验证配置能持久化保存,确认无误后才能考虑断电,绝不能刷完就直接拔电源。**

## 十、最终完整可复用的操作清单

### 10.1 一次性准备(树莓派联网时)

```bash
sudo apt update
sudo apt install -y tftpd-hpa tcpdump

sudo mkdir -p /srv/tftp
sudo chmod 755 /srv/tftp
sudo tee /etc/default/tftpd-hpa > /dev/null <<'EOF'
TFTP_USERNAME="tftp"
TFTP_DIRECTORY="/srv/tftp"
TFTP_ADDRESS="0.0.0.0:69"
TFTP_OPTIONS="--secure --create"
EOF
sudo systemctl restart tftpd-hpa

# 下载正式固件,文件名先按官方/教程给的填,后续用tcpdump确认后再改名
sudo wget -O /srv/tftp/<u-boot请求的确切文件名>.itb <固件下载地址>

# 校验
sha256sum /srv/tftp/<文件名>.itb
```

### 10.2 配置eth0(确保用WiFi的IP保持SSH,不要用eth0自己的连接执行这些命令)

```bash
sudo nmcli con add type ethernet ifname eth0 con-name recovery ip4 192.168.1.254/24
sudo nmcli con up recovery
# 关键:精确路由,只处理"去192.168.1.1"这一条,不影响其他流量,且metric要设小(优先)
sudo ip route add 192.168.1.1/32 dev eth0 metric 50
```

### 10.3 通电救砖 + 确认文件名

```bash
# 另开一个SSH会话(WiFi的IP)
sudo tcpdump -i eth0 -n udp port 69
```
手动操作路由器:拔电源 → 按住Reset → 插电源 → 保持10秒 → 松开

**核对tcpdump抓到的RRQ文件名,如与本地不一致,立即复制改名**:
```bash
sudo cp /srv/tftp/原文件 /srv/tftp/<tcpdump抓到的确切文件名>
```

### 10.4 观察传输完成

持续观察tcpdump,出现**小于1472字节的最后一个DATA包**即代表传输完成。

### 10.5 视u-boot行为决定后续

- 如果这次抓到的是 `xxx-sysupgrade.itb` 格式 → **u-boot直接写入flash并重启**,等待1-2分钟后 `ping`+`ssh` 测试新系统
- 如果抓到的是 `xxx-initramfs.itb` 格式 → 传输完成后会进入**临时内存系统**,需要SSH进去后手动执行sysupgrade:
  ```bash
  ssh root@192.168.1.1
  # (从树莓派scp正式固件过去,注意-O参数)
  # 在本地树莓派执行:
  scp -O /srv/tftp/<正式固件>.itb root@192.168.1.1:/tmp/
  # 回到路由器SSH会话
  sysupgrade -n /tmp/<正式固件>.itb
  ```

### 10.6 刷机完成后的收尾(务必做完,不要跳过)

```bash
ssh root@192.168.1.1
passwd          # 立刻设置密码
reboot          # 正常重启一次,验证配置持久化
# 等待1-2分钟后重新ping+ssh,确认密码还在、系统稳定
```

**只有验证过reboot后配置依然保留,才能放心断电或做后续配置。**

### 10.7 恢复树莓派环境

```bash
sudo ip route del 192.168.1.1/32 dev eth0 2>/dev/null
sudo nmcli con down recovery
sudo nmcli con delete recovery
```

## 十一、这次经历最值得记住的几条通用原则

1. **善用抓包(tcpdump)验证假设,不要完全信任教程里写死的文件名/参数**,不同硬件版本/固件版本可能不一致
2. **网络调试时,永远保留一条独立于"正在调试的那条链路"之外的控制通道**(这次是靠WiFi保住SSH,亦可用接显示器键盘做为后备)
3. **`route-metric`/`never-default` 只管默认路由,不管同网段内的路由选择**,多网卡同网段场景要用精确的 `/32` 主机路由解决
4. **两个不同设备IP撞车,是很多"诡异"网络问题的根源**,遇到反复不稳定、时通时不通的情况要优先怀疑这个
5. **`19字节`的UDP包在TFTP协议里通常是错误提示,不是正常传输**,肉眼观察数据包大小能快速判断传输是否正常发生
6. **修改完设备关键配置后,必须用正常流程(reboot)验证生效并持久化,再考虑断电**,直接拔电源是导致本次最严重一次返工的原因
7. **当排查成本明显超过重来一次的成本时,清空重来往往是更优选择**(这次的eth0诡异DOWN问题最终就是这样解决的)
