## 建议:直接用方式1(TFTP整刷),不用方式2

理由很直接——**方式2(系统内sysupgrade)依赖的正是这次刚修复的那个脚本逻辑,如果这次修复还有什么疏漏,又会重演"刷了但没生效"的坑**。而方式1直接走u-boot的TFTP,和这个脚本完全无关,更可靠。而且你现在的树莓派TFTP环境已经搭好了,轻车熟路。

```bash

```

## 保险起见,直接删掉那条容易捣乱的 `/24` metric 700 路由

这条路由其实是没必要存在的干扰项(我们只需要精确的`/32`路由来处理和路由器的通信),试试直接删掉:

```bash
sudo ip route del 192.168.1.0/24 dev eth0
ip route show
```

删除后应该只剩:

```
default via 192.168.1.1 dev wlan0 ...
192.168.1.0/24 dev wlan0 ...
192.168.1.1 dev eth0 scope link metric 50
```

这样"去192.168.1.1"只有一条路径可选(eth0的精确路由),不会有歧义。

删除后不需要重新触发救砖,路由器还在每5秒重试,直接观察tcpdump看这次是否恢复正常。把 `ip route get 192.168.1.1` 和删除后的tcpdump结果发我。

192.168.1.1 dev wlan0 src 192.168.1.165 uid 1000  
cache

找到了,而且证据非常直接——**内核实际选择的是 `wlan0`,不是eth0**!

即使我们加了metric=50的精确路由(理论上应该比wlan0的默认路由metric 600优先得多),内核最终却走了wlan0。这说明**Linux的路由查找规则比想象的更复杂**——很可能是因为 `ip route get` 默认这条查询带了 `src 192.168.1.165`(也就是以wlan0的IP作为默认源地址考量),这种情况下策略路由的选择逻辑跟单纯metric大小不完全等价,系统可能优先选了"和默认路由src地址匹配"的那条路径,而不是单纯metric最小的路径。

## 直接删除那条网段路由,消除歧义来源

```bash
sudo ip route del 192.168.1.0/24 dev eth0
ip route get 192.168.1.1
```

这次删除后,eth0上不再有能匹配 `192.168.1.0/24` 这个网段的路由(只留最精确的`192.168.1.1/32`那一条),`ip route get 192.168.1.1` 应该会变成走eth0。

如果这次还是不行,我们换一个更直接、更暴力但一定有效的方法——**给这条精确路由显式指定源地址**:

```bash
sudo ip route replace 192.168.1.1/32 dev eth0 src 192.168.1.254 metric 50
ip route get 192.168.1.1
```

不过除了我们已经处理过的"路由选择"层面,这次很可能还触发了一个**更底层的内核安全机制**——**反向路径过滤(rp_filter)**。

## 这是什么

Linux内核默认会检查:"这个包是从哪个网卡收到的,如果按照路由表,回复这个包应该从另一个网卡出去,那这个包就可能是伪造的/有问题的,直接丢弃"。这个机制叫 `rp_filter`,在**你的场景里几乎是精确触发条件**——因为路由表里同时有"经wlan0去192.168.1.1"(默认路由)和"经eth0去192.168.1.1"(我们加的精确路由),这种不对称路由,在严格模式下会被rp_filter直接判定为可疑并丢弃。

## 检查当前设置

```bash
sysctl net.ipv4.conf.eth0.rp_filter && sysctl net.ipv4.conf.wlan0.rp_filter && sysctl net.ipv4.conf.all.rp_filter && sysctl net.ipv4.conf.default.rp_filter
```

如果这几个值里有 `1`(严格模式),这就是问题所在。

## 解决:临时关闭 eth0 的 rp_filter

```bash
sudo sysctl -w net.ipv4.conf.eth0.rp_filter=0 && sudo sysctl -w net.ipv4.conf.all.rp_filter=0
```

设置为 `0`(不过滤)或 `2`(宽松模式)都可以解决这个问题。执行后不需要重新触发救砖,路由器还在重试,直接观察tcpdump看是否恢复。

## 方式A:命令行直接改(更快,适合你现在已经在SSH里)

### 第一步:先确认F50已经在线且eth2状态正常

先把F50接好(开机、联网、进入USB共享模式),然后:

```bash
ip link show eth2
```

确认是 `UP` 状态(不是之前拔掉时看到的`DOWN`)。

### 第二步:查看当前网络配置

```bash
cat /etc/config/network
```

把结果发我看看,重点看现在 `wan` 那个 `config interface` 段落里 `option device` 写的是什么(应该是`eth1`,对应你之前接的那根有网网线的口)。

### 第三步:把WAN的设备改成eth2

```bash
uci set network.wan.device='eth2'
uci commit network
/etc/init.d/network reload
```

如果F50这边默认是DHCP方式获取上网参数(通常是),`option proto` 那栏应该已经是 `dhcp`,不需要改。

### 第四步:验证是否成功获取到IP、能上网

```bash
ip addr show eth2
ping -c 3 www.baidu.com
```

如果 `eth2` 拿到了IP地址,并且ping通了外网,说明配置生效。

## 方式B:LuCI网页操作(更直观)

1. 浏览器打开 `http://192.168.1.1`,登录LuCI
